# W0-033: follow-up defects in 06f7d1a; Stage 1–4 acceptance remains blocked

## Reviewed commit

`06f7d1a90131accf0e9306c18574b25717a5b861`
(`xaverius: W0-029 observation/removal normative fixes (A-G)`).

This commit is useful progress, but it does not close W0-029/W0-030. Do not report Stage 3 or Stages 1–4 complete. No CI status checks or workflow runs are attached to this SHA.

## Concrete remaining defects

### 1. Source-Key length and lifecycle are still unsafe

In `XaveriusRegistryObserveDevice()`:
- The unresolved branch still allocates/copies using `identity_evidence_size` (lines around 751–757), despite the new `source_key_size` parameter. This retains the original out-of-bounds/false-key defect on the PENDING path.
- `source_key_size` has no nonzero or maximum-bound validation before allocation/copy.
- A previously unknown key is silently registered with the caller-supplied `source_generation`. This is not server-owned generation allocation or explicit source registration. Observe must not create/rotate sources.
- `registry` is ignored.
- outputs are not initialized on all failure paths.
- duplicate observation IDs / replay semantics are not enforced.

Implement the minimum explicit source register/retire lifecycle required by W0-029. Allocate a non-reusable generation server-side; Observe must resolve an existing active source and require exact key bytes, exact key length and exact active generation. Define and enforce a documented maximum key size. Do not use unbounded string operations.

### 2. Matched observations omit device_generation

The matched-device branch stores `obs->device = dev` but never sets
`obs->device_generation`. Removal confirmation consequently cannot reliably
validate the observation's device incarnation. Set and validate it consistently
for every linked observation. Do not store a raw pointer without a lifetime
guarantee; source retirement/device retirement must not leave dangling
observation pointers.

### 3. RemoveObservation still lacks exact key-length validation

Its API has no `source_key_size`; it compares the stored key length against
caller memory with `memcmp(..., obs->source_key_size)`. A shorter caller key
can be read out of bounds, and a longer key is not distinguished. Add the
same explicit bounded key+length contract used by Observe and source lifecycle.
Require active source identity/generation and exact observation identity.
Enforce duplicate/replay/idempotency rules from W0-029.

### 4. ConfirmDeviceRemoved is not validating the normative evidence structure

`xaverius_find_observation_by_evidence()` currently accepts only a bytewise
match to `XaveriusDeviceIdentity`. W0-029 requires the complete
`XaveriusDeviceRemovalEvidence` contract, including size/version/fields,
source key, source generation, observation ID, source event sequence and
physical-device generation. The current code does not validate source
registration/authority or event sequence and can accept identity bytes as
removal evidence.

Implement the actual normative evidence structure and validate its header
before any cast/field access. Resolve the active source and exact observation;
derive authority from registered source capabilities and server trust policy.
Reject untrusted, stale, conflicting or insufficient evidence without mutation.
A repeated confirmation must not report a second successful transition.

### 5. Pending/Ambiguous and resolution semantics remain incomplete

The no-match path always returns PENDING; it never distinguishes AMBIGUOUS
from insufficient evidence. It also stores no later-resolution mechanism.
Implement the exact Spec semantics, including whether/how unresolved
observations become linked to a canonical device. Do not invent a second
device or publish ambiguous evidence.

### 6. Initialization, teardown and observation lifetime remain incomplete

`XaveriusRegistryInit()` does not initialize the observation list/count.
`XaveriusRegistryFini()` only zeros counters and leaks/abandons source and
observation allocations; it does not drain/retire them. It also claims no
published records exist despite Stage 4 publication being implemented.
Implement ordered cleanup/drain and ensure observations cannot outlive the
device/source they reference. Make repeated Init/Fini behavior explicit.

### 7. ModuleRole/binding ownership rollback remains suspect

The new DIX destructor frees a binding but does not call
`XaveriusModuleRoleRelease()`, despite its comment claiming it releases the
ModuleRole reference. Registration failure paths after
`XaveriusModuleRoleRetain()` must balance that retain. Audit every failure
edge, including binding allocation failure, device allocation, identity
copy, snapshot validation/copy, callback failure and publication failure.
Use one clear rollback path or demonstrably balanced local unwinds.

### 8. Duplicate declaration remains

`xaverius_intern.h` still declares
`XaveriusRegistryRemoveDeviceBackendBinding()` twice. Remove the duplicate
and audit exactly the three agreed headers for duplicate/conflicting
declarations. Do not add a fourth header.
